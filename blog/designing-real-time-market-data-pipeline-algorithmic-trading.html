Designing a Real-Time Market Data Pipeline for an Algorithmic Trading Platform

System Design FastAPI Redis WebSockets Event-Driven Architecture
Engineering Context: This case study describes the underlying backend architecture of Growth Quantix. It focuses on streaming data design, concurrency, and broker abstraction rather than financial strategy performance or sub-microsecond HFT latency claims.

Real-time algorithmic trading engines rely on continuous feeds of market ticks to compute technical indicators, evaluate entry/exit rules, and broadcast live price changes to user dashboards. In a multi-user, multi-strategy system, connecting strategy execution logic directly to a single broker WebSocket connection introduces severe architectural coupling.

If a strategy worker blocks on heavy calculations or database writes, the main WebSocket connection drops ticks, triggers TCP backpressure, or crashes due to buffer overflows.

To ensure reliability, fault tolerance, and clear operational boundaries, I designed an event-driven market data pipeline for Growth Quantix using FastAPI, Asyncio, Redis Pub/Sub, PostgreSQL, and WebSockets.

2. Upstox Market Feed V3 & Ingestion Layer

Upstox Market Feed V3 streams tick data encoded in binary Protocol Buffers (Protobuf) over WebSocket connections. The ingestion service handles connection setup, heartbeat ping-pongs, and binary decoding:

  1. Authorized Handshake: Establishes WebSocket connection using a valid access_token obtained via the OAuth2 service.
  2. Dynamic Subscriptions: Sends subscription frames containing lists of instrument keys (e.g., NSE_EQ|INE002A01018) and subscription modes (Full LTP, Market Depth).
  3. Binary Protobuf Decoding: Deserializes raw binary payloads into structured Python dictionaries.
  4. Tick Normalization: Maps broker-specific field names into a unified, platform-agnostic schema containing instrument_token, last_price, volume, open_interest, and timestamp.

3. Redis Event Bus & Strategy Decoupling

Publishing normalized ticks directly to a Redis Pub/Sub topic decouples data ingestion from downstream strategy execution:

  • Non-Blocking Ingestion: The ingestion service immediately pushes ticks into Redis channels (e.g., ticks:NSE_EQ:RELIANCE) without waiting for strategy completion.
  • Fan-Out Distribution: Multiple independent strategy workers can subscribe to the same Redis channel simultaneously without increasing load on the upstream broker WebSocket.
  • Buffer Isolation: If a strategy crashes or experiences CPU lag, the ingestion service continues operating without interruption.
import redis.asyncio as aioredis
import json

class RedisTickPublisher:
    def __init__(self, redis_url: str):
        self.redis = aioredis.from_url(redis_url)

    async def publish_tick(self, tick: NormalizedTick):
        channel = f"ticks:{tick.instrument_key}"
        payload = tick.json()
        await self.redis.publish(channel, payload)

Features of the execution layer include:

  • Pre-Trade Safety Checks: Verifies active market sessions, account funds, and max risk limits before allowing order placement.
  • Symmetric Paper Trading Parity: Paper trading simulates 0.05% slippage and broker fee deductions to mirror real market execution realistically.
  • Single Exit Authority: Order status tracking and emergency exit handlers operate with single-authority locking to prevent duplicate order submissions.

5. Reconnection Lifecycle & Fault Tolerance

Internet connectivity hiccups can cause WebSocket drops. The system implements an automatic reconnection engine:

  • Exponential Backoff with Jitter: Retries dropped connections using randomized exponential delays to avoid thundering herd problems on reconnect.
  • Historical Candle Backfill: Upon reconnecting after an outage, the strategy engine fetches missing historical candles via Upstox REST APIs to restore technical indicator states before resuming live tick processing.
  • Heartbeat Monitoring: Monitors connection ping/pong signals every 10 seconds; forces socket reset if pong frames are missed for over 30 seconds.

6. Future Scaling & Technical Tradeoffs

While the current setup using FastAPI, Redis Pub/Sub, and PostgreSQL easily handles real-time needs for multi-instrument monitoring, scaling to thousands of concurrent instruments presents clear design evolution paths:

  1. Redis Streams over Pub/Sub: Switching to Redis Streams provides message persistence and consumer groups for guaranteed at-least-once processing across strategy worker clusters.
  2. Time-Series Database Integration: Moving historical tick storage from PostgreSQL to TimescaleDB or ClickHouse enables faster time-bucket aggregation for backtesting.
