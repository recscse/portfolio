Designing an AI Trading System Without Letting the Model Control Everything

AI Systems Architecture Risk Engine Trading Safety FastAPI Deterministic Boundaries
Disclaimer: This article discusses software architecture and experimental research. It does NOT constitute financial advice, trading signals, or investment recommendations.

When integrating artificial intelligence into trading software, a dangerous temptation is to connect model inference outputs directly to order execution endpoints. Promoters of "AI-driven trading" often imagine an end-to-end model that reads ticks, predicts price direction, and submits live broker orders autonomously.

In production software engineering, this design is unacceptably fragile. Machine learning models are probabilistic function approximators. They suffer from distribution drift, hallucinated signals during market volatility, and zero awareness of account risk limits or active trading sessions.

The correct architectural pattern treats machine learning outputs as untrusted candidate proposals that must pass through deterministic risk filters and safety barriers before any order is submitted.

2. Common AI Failure Modes in Financial Systems

To design effective safety boundaries, we must explicitly account for AI failure modes:

  • Out-of-Distribution Data: During sudden news shocks or earnings announcements, historical pattern correlations break down, causing models to generate high-confidence invalid signals.
  • Stale Data Feed Replay: If a WebSocket drops packets and re-submits old price ticks, the model may perceive a fake momentum breakout.
  • Off-Market Hours Generation: Models lacking explicit clock constraints will happily generate "BUY" signals at 2:00 AM on Sunday.

3. Implementing the Risk Engine Barrier

The risk engine evaluates every model recommendation against hard rules. If any check fails, the trade proposal is dropped and logged with a rejection code: 

class SystemKillSwitchException(Exception):
    pass

class SafetyRiskEngine:
    def __init__(self, daily_pnl_limit: float, max_order_val: float):
        self.daily_pnl_limit = daily_pnl_limit
        self.max_order_val = max_order_val
        self.kill_switch_active = False

    def validate_proposal(self, proposal: TradeProposal, current_pnl: float) -> bool:
        # Rule 1: Emergency Kill Switch
        if self.kill_switch_active:
            raise SystemKillSwitchException("Trading halted: Emergency Kill Switch is ACTIVE")

        # Rule 2: Daily Max Drawdown Guard
        if current_pnl <= -self.daily_pnl_limit:
            logger.error(f"Proposal rejected: Daily PnL {current_pnl} breached limit {-self.daily_pnl_limit}")
            return False

        # Rule 3: Session Time Check (Indian Market Hours 9:15 - 15:30 IST)
        now_ist = datetime.now(pytz.timezone("Asia/Kolkata")).time()
        if not (time(9, 15) <= now_ist <= time(15, 25)):
            logger.warning(f"Proposal rejected: Inactive market hours ({now_ist})")
            return False

        # Rule 4: Capital Limit Guard
        if proposal.estimated_cost > self.max_order_val:
            logger.warning("Proposal rejected: Order value exceeds capital threshold")
            return False

        return True

4. Paper Trading Verification & Auditability

Before any model recommendation is enabled for live broker execution, it runs in a Paper Trading Sandbox for an evaluation period. The paper sandbox applies:

  • Slippage Simulation: Adds 0.05% adverse price movement to entry/exit execution prices.
  • Brokerage & STT Deduction: Subtracts real brokerage charges and Securities Transaction Tax (STT) from PnL calculations.
  • Versioned Audit Logs: Records model version, feature state snapshot, risk decision, execution fill price, and realized PnL in PostgreSQL tables.

Conclusion

AI models are valuable tools for signal extraction and candidate scoring, but they must never exercise unrestricted execution authority. Gating model proposals behind deterministic risk filters, session checks, and paper-trading verifiers ensures system resilience and financial safety.
