Designing a Safe AI-Assisted Trading System: From Stock Selection to Execution

AI System Architecture Risk Management FastAPI Trading Infrastructure Safety Controls
Financial & Engineering Disclaimer: This project is an engineering and research system designed to explore software safety patterns in quantitative pipelines. It does NOT constitute financial advice, investment recommendations, or a claim of market trading profitability.

Applying machine learning models to financial markets presents unique backend engineering challenges. Unconstrained AI models can hallucinate signals, output high-confidence predictions during extreme illiquidity, or place orders outside valid market hours.

In automated trading software, AI output must never directly trigger order placement without passing through deterministic risk validation layers.

In this article, I break down the engineering architecture of an AI-assisted stock selection and execution pipeline, focusing on data validation, feature engineering, risk isolation, paper-trading simulation, and audit controls.

1. The Multi-Stage Pipeline Architecture

The system enforces strict stage-gating. If any validation stage fails, the process halts immediately without advancing to order execution.

2. Data Validation & Feature Pipeline

Machine learning inference is sensitive to noisy input. Raw candle data fetched from historical REST APIs undergoes validation before feature calculation:

  • Stale Candle Detection: Verifies that historical candle timestamps match expected market interval sequences. Missing candles are backfilled via API requests.
  • Outlier Removal: Filters out bad ticks where price movements exceed impossible single-candle thresholds (e.g., erroneous 50% price drops caused by broker feed errors).
  • Feature Normalization: Technical indicators (EMA, RSI, ATR, Volume Spikes) are computed deterministically and scaled before model input.
def validate_candle_data(df: pd.DataFrame) -> pd.DataFrame:
    """Ensures candle data integrity before model feature extraction."""
    if df.empty or len(df) < 50:
        raise ValueError("Insufficient candle history for feature extraction")
        
    # Check for NaN or zero prices
    if df[['open', 'high', 'low', 'close']].isna().any().any():
        df = df.bfill().ffill()
        
    # Verify non-zero volume
    df = df[df['volume'] > 0]
    return df

3. Stock Selection Model & Direction Logic

The selection model scores candidate stocks based on momentum, price structure, and relative market strength.

In neutral market conditions, relying purely on binary directional signals can lead to over-trading whipsaws. To mitigate this, the engine uses a neutral sensitivity threshold (0.25%) combined with price structure verification to select Call (CE) or Put (PE) option directions only when momentum confirmation exists.

4. Deterministic Risk & Guard Filters

The most crucial architectural decision is placing a hard deterministic barrier between AI prediction outputs and order execution: 

class TradeRiskGuard:
    def __init__(self, max_capital_per_trade: float, daily_loss_limit: float):
        self.max_capital = max_capital_per_trade
        self.daily_loss_limit = daily_loss_limit

    def evaluate_candidate(self, candidate: TradeCandidate, account_status: AccountStatus) -> bool:
        # Rule 1: Market Session Guard
        if not self.is_market_open():
            logger.warning("Trade rejected: Market session inactive")
            return False

        # Rule 2: Daily Drawdown Limit
        if account_status.daily_pnl <= -self.daily_loss_limit:
            logger.warning("Trade rejected: Daily loss limit reached")
            return False

        # Rule 3: Position Sizing & Margin Cap
        if candidate.estimated_cost > self.max_capital:
            logger.warning("Trade rejected: Capital requirement exceeds safety threshold")
            return False

        return True

5. Execution Safety & Paper Trading Parity

To validate system stability without risking real capital, the execution handler defaults to a simulated Paper Trading Mode:

  • Dynamic Balance Ledger: Tracks entry capital deductions and exit capital returns (investment + PnL) dynamically in PostgreSQL.
  • Lot Size Resolution: Leverages active instrument registries to resolve broker lot sizes accurately, preventing order rejections.
  • Single Exit Authority: Order status tracking and emergency exits are governed by a central authority to avoid double-exit races.

6. Observability, Logging, & End-of-Day Evaluation

For operational transparency, every trade candidate recommendation is logged alongside model version, input feature state, risk decision, execution status, and realized PnL.

An automated End-of-Day (EOD) evaluation job correlates model predictions against actual market outcomes, helping engineers identify model drift over time without compromising live execution safety.
